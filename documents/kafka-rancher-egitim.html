1. Giriş ve Eğitimin Amacı

Bu eğitim, bir yazılımcı grubuna “Kafka’yı ve Kubernetes’i birlikte düşünerek uygulamayı taşıma” fikrini anlatıyor. Öğrenme hedefi: Docker Compose ile çalışan bir Kafka laboratuvarını Rancher Desktop + k3s ortamına taşımak, pod’lara dağıtmak, izlemek, ölçeklendirmek ve olay akışını kavramak.

Kazanımlar
  • Rancher Desktop kurulumunu ve k3s yapısını anlayacaksınız.
  • Kafka broker, topic, partition, consumer group kavramlarını günlük dille ve örnekle öğreneceksiniz.
  • Spring Boot producer/consumer uygulamasını Kubernetes’e taşıyacaksınız.
  • Pod, Service, PVC, Deployment, StatefulSet, Probe, Secret, ConfigMap, Job kavramlarını konuşma diliyle öğrenip uygulayacaksınız.
  • Prometheus/Grafana ile observability ve sorun giderme pratiği yapacaksınız.
💡 İpucu: Bu eğitimde “container” ve “pod” arasındaki farkın net olması çok önemlidir. Container tek uygulama kapsülüdür; pod ise tek bir ağ kimliğiyle birlikte çalışan kapsüllerin bir araya gelmesidir.

Ön koşul: Java 17, Maven, Docker veya nerdctl, kubectl, temel Linux terminal bilgisi. Tahmini süre: 2–3 saat anlatım + 1–2 saat pratik ekip çalışması.

4. Kafka Temelleri (konunun kalbi)

Kafka, “Olay akışı / event streaming” için tasarlanmış bir mesajlaşma ve veri akışı platformudur. Bir request/response çağrısı ile karşılaştırırsak:

Request/ResponseEvent-driven
Hemen cevap beklenirMesaj teslimi asenkron olur
Önce istemci, sonra serverProducer ve consumer birbirine ihtiyaç duymaz
Bağlantı, darboğaz ve gecikmeArabelleğe alma ve buffering
Monolitik akışBağımsız servisler ve ölçeklenme

Broker, topic, partition, offset

  • Broker: Kafka sunucusu, mesajları yazan ve tüketen düğüm.
  • Topic: Mesaj akışı adı. Örnek: orders.events
  • Partition: Bir topic’in paralel taşıyıcıları. Aynı topic’in aynı key’i taşıyan mesajları aynı partition’a götürür.
  • Offset: Her partition içinde mesajın sırası. Consumer, “ben bu offset’tan itibaren okumaya devam” der.

Partition ve consumer group

Bu projede topic orders.events 3 partition’a sahiptir. Consumer group order-processor olarak tanımlıdır. Bu durumda en fazla 3 consumer aynı anda eşzamanlı partition’ları paralel işleyebilir. Dördüncü consumer ise boşta kalır çünkü 3 partition vardır ve Kafka her partition için tek bir consumer assignment yapar.

🧪 Deneyin: Bir topic 3 partition, consumer group 4 pod ⇒ en fazla 3 pod aktif, 1 pod boşta kalır. Bu yüzden “consumer 4’un neden boşta?” sorusu burada net çözülür.

Delivery guarantees

  • At-most-once: Mesaj alınır ama commit / işleme garantisi yok.
  • At-least-once: Mesaj en az bir kez işlenir; duplicate olabilir.
  • Exactly-once: Daha zordur; idempotent writer + transactional processing gerektirir.

Bu proje, enable.idempotence: true ve read_committed ile daha güvenilir davranış sağlar. Consumer tarafında manual ack kullanılıyor: acknowledge() çağrılmadan mesaj commit edilmez.

5. Projenin Kod Analizi: Kafka ile İlgili Sınıflar

Bu bölümde çalıştığımız gerçek sınıfları ve ilişkilerini inceliyoruz. Her biri koddan doğrulanan sınıf/yöntem bilgilerini kullanır.

Order / OrderController

Dosya: Order/src/main/java/com/works/OrderController.java. Bu sınıf HTTP endpoint sağlar.

@Controller
@RequestMapping("orders")
public class OrderController {
    private final OrderEventPublisher orderEventPublisher;

    @PostMapping("add")
    public ResponseEntity addOrder(@RequestParam String orderId,
                                        @RequestParam(defaultValue = "CREATED") String status) {
        if (orderId == null || orderId.isBlank()) {
            return ResponseEntity.badRequest().build();
        }

        orderEventPublisher.publish(orderId, status)
            .thenAccept(result -> System.out.println("Order event published successfully for orderId: " + orderId))
            .exceptionally(ex -> {
                System.err.println("Failed to publish order event for orderId: " + orderId + ", error: " + ex.getMessage());
                return null;
            });
        return ResponseEntity.accepted().build();
    }
}

Özeti: request kabul edilir, sonra üretim başlatılır, HTTP 202 Accepted dönülür. Asenkron mesajlaşma burada görülür.

⚠️ Dikkat: Bu kod “başarıyı” HTTP yanıtında değil, Kafka publish sonucunda raporlar. Bu yüzden “çok geç yanıt” gibi durumlar yaşanabilir, fakat sistem asenkron çalışır.

Öğrenciye soru: “Neden 202 Accepted döndürüldü? Bu, broker’a yazılma işlemini beklemiyor mu?”

Order / OrderEventPublisher

Dosya: Order/src/main/java/com/works/OrderEventPublisher.java. Producer tarafı.

@Service
public class OrderEventPublisher {
    private final KafkaTemplate kafkaTemplate;

    public CompletableFuture<SendResult<String, OrderEvent>> publish(String orderId, String status) {
        var event = new OrderEvent(orderId, status, Instant.now());
        return kafkaTemplate.send("orders.events", orderId, event)
            .whenComplete((result, error) -> {
                if (error != null) {
                    System.err.println("Kafka publish failed: " + error.getMessage());
                } else {
                    var metadata = result.getRecordMetadata();
                    System.out.printf("Published topic=%s partition=%d offset=%d%n",
                        metadata.topic(), metadata.partition(), metadata.offset());
                }
            });
    }
}

Burada KafkaTemplate.send("orders.events", orderId, event) çağrısı yapılır. Key olarak orderId verilir; bu aynı key aynı partition’a demektir. Böylece aynı sipariş akışı aynı partition üzerinde sıralı ilerler.

Öğrenciye soru: “Bu key neden orderId?”

Order / OrderEvent

Dosya: Order/src/main/java/com/works/OrderEvent.java ve Consumer tarafı aynı isimle mevcut. Şimdi Java record kullanımı:

public record OrderEvent(String orderId, String status, Instant occurredAt) {}

Bu event, JSON olarak serializable hale gelir. JsonSerializer ve JsonDeserializer kullanılır. record, null-safe bir veri taşıyıcısıdır.

Order / KafkaTopics

Dosya: Order/src/main/java/com/works/KafkaTopics.java ve Consumer tarafında benzeri.

@Configuration
public class KafkaTopics {
    @Bean
    NewTopic ordersTopic() {
        return TopicBuilder.name("orders.events")
                .partitions(3).replicas(1).build();
    }

    @Bean
    NewTopic ordersDltTopic() {
        return TopicBuilder.name("orders.events.DLT")
                .partitions(3).replicas(1).build();
    }
}
❌ Sık yapılan hata: Docker Compose dosyasındaki topic oluşturma komutu orders.eventsx yazarken, Java tarafında DLT ismi orders.events.DLT şeklindedir. Bu bir çelişkidir. Bu durumda infra ve uygulama tarafı arasında “tek doğru topic adlandırması” anlaşması gerekir; laboratuvarda açıkça not edilmelidir.

Consumer / OrderEventConsumer

Bu sınıf @KafkaListener ile mesaj dinler. Dosya: Consumer/src/main/java/com/works/OrderEventConsumer.java.

@KafkaListener(topics = "orders.events", groupId = "order-processor", concurrency = "3")
public void receive(ConsumerRecord<String, OrderEvent> record, Acknowledgment acknowledgment) {
    try {
        Thread.sleep(3000);
        var event = record.value();
        acknowledgment.acknowledge();
    } catch (Exception e) {
        throw new RuntimeException("Failed to process order event", e);
    }
}

Özellikler:

  • topics = "orders.events": dinlenecek topic.
  • groupId = "order-processor": aynı consumer group.
  • concurrency = "3": 3 thread paralel çalışma.
  • Acknowledgment: manual commit için kullanılıyor.
  • Thread.sleep(3000): iş yükünün 3 saniye sürmesini simüle eder.
💡 İpucu: Burada aynı grup için 3 consumer pod çalıştırıldığında Kafka partition ataması yapılır. Her partition sadece tek bir consumer’a atanır; aynı consumer birden çok partition’a bakabilir ama tek partition birden çok consumer’a verilemez.

Hata yönetimi ve DLT

Java tarafında KafkaErrorConfiguration kullanılmıştır. DLT kavramı: işlemesi başarısız olan mesajları ayrı bir dead-letter topic’e yazmaktır.

var recoverer = new DeadLetterPublishingRecoverer(template, (record, exception) ->
    new TopicPartition(record.topic() + ".DLT", record.partition()));
return new DefaultErrorHandler(recoverer, new FixedBackOff(1_000L, 2L));

Buradaki amaç, “hatayı sürekli tekrar döndürmek yerine, en sonunda bir DLT’ye alıp operasyonel müdahale için ayırmak”tır.

advertised.listeners problemi

Compose’da KAFKA_ADVERTISED_LISTENERS şu şekilde çalışıyor:

  • Producer/consumer yerel bilgisayardan bağlanıyorsa: localhost:9092
  • Container içinden bağlanıyorsa: broker:19092

Kubernetes’te bunun tek yönde çözümü yoktur; çünkü aynı broker için hem pod içi DNS hem de dışarıdan port-forward erişimi ayrı adreslerle çalışmalıdır. Bu yüzden işin doğru modeli şudur:

KAFKA_LISTENERS: "CONTROLLER://:29093,INTERNAL://:19092,CLIENT://:9092"
KAFKA_ADVERTISED_LISTENERS: "INTERNAL://kafka-0.kafka-headless.kafka-lab.svc.cluster.local:19092,CLIENT://localhost:9092"
KAFKA_INTER_BROKER_LISTENER_NAME: "INTERNAL"

Kısacası:

  • Cluster içi uygulama: kafka:19092 veya kafka-0.kafka-headless.kafka-lab.svc.cluster.local:19092
  • Dışarıdan port-forward ile lokal bilgisayardan: localhost:9092
❌ Sık yapılan hata: Broker üretim tarafında kafka:9092 gibi bir listener açılsa ama broker localhost:9092 reklam yapsa, client bağlantıyı kurar ama sonra “Connection refused”, “timeout”, “leader not available” gibi hatalar görür. Çünkü client metadata’da reklam edilen adrese bağlanmaya çalışır.

depends_on’ın Kubernetes karşılığı

Compose’daki depends_on: service_healthy ifadesi, Kubernetes’te doğrudan yoktur. Orada karşılığı:

  • readinessProbe / livenessProbe
  • initContainer ile broker hazır olana kadar bekleme
  • uygulama tarafında retry / backoff

Bu yüzden kafka-init-job.yaml içinde initContainer çalışır; broker hazır olana kadar bekler; sonra topic oluşturma çalıştırılır.

Compose volume’dan PVC’ye

Compose’da kafka-data:/var/lib/kafka/data var. Kubernetes’te buna karşılık PVC gelir. Rancher Desktop üzerinde default StorageClass genellikle local-path olur. Bu yüzden:

volumeClaimTemplates:
  - metadata:
      name: kafka-data
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: local-path
      resources:
        requests:
          storage: 5Gi

Bu, Kafka broker’ın verisini host üzerinde kalıcı tutar; pod silinip yeniden oluşsa bile verinin yeniden yüklenmesi beklenir.

Durumlar:

  • Pending: Scheduler pod’u yerleştirmeye çalışıyor.
  • ContainerCreating: Image çekiliyor / container başlatılıyor.
  • Running: Uygulama çalışıyor.
  • CrashLoopBackOff: Uygulama sürekli çöküyor ve yeniden başlıyor.
  • ImagePullBackOff: Görüntü yerelde yok, K8s çekemedi.
  • Completed: Job tamamlandı.

Ölçekleme laboratuvarı

kubectl scale deployment consumer -n kafka-lab --replicas=1
kubectl scale deployment consumer -n kafka-lab --replicas=3
kubectl scale deployment consumer -n kafka-lab --replicas=4
kubectl get pods -n kafka-lab -l app=consumer -o wide

3 partition olduğu için 4. consumer boşta kalacaktır. Bu, Kafka consumer group mantığıyla doğrudan ilişkilidir. Rebalance’i log’lardan izleyebilirsiniz.

Dayanıklılık laboratuvarı

kubectl get pvc -n kafka-lab

13. Özet, Alıştırmalar ve Sınıf Soruları

Özet

  • Docker Compose ile çalışan app, Kafka broker ve observability stack’i Kubernetes’e taşındı.
  • Broker için StatefulSet + PVC + headless Service yapısı kullanıldı.
  • Order ve Consumer için Deployment + Service + readiness/liveness + ConfigMap kullanıldı.
  • Broker için advertised.listeners ve port-forward akışı doğru modellenmeye çalışıldı.
  • Prometheus ve Grafana ile uygulama + Kafka metrikleri izleniyor.

Alıştırmalar

  1. Consumer’ın replicas sayısını 1 → 3 → 4 değiştirip partition atamasını gözlemleyin.
  2. Topic üzerinde 10 adet event üretip k8s içindeki Kafka CLI ile offsetleri görün.
  3. Kafka pod’unu silip PVC’nin veriyi koruduğunu doğrulayın.
  4. Grafana’da lag panelini izleyerek consumer ölçeklendiğinde düşüşü görün.
  5. ConfigMap değeri değiştirip deployment’ın yeni değeri alıp almadığını test edin.

Çoktan seçmeli soru örnekleri

  1. Kafka topic içindeki her partition için hangi ifade doğrudur?
    • A. Sadece bir consumer tarafından okunur.

    • C. Topic her zaman tek partition’tan oluşur.
  2. StatefulSet neden Kafka için uygundur?
    • A. Çünkü statik isim ve persistence gerektirir.
    • B. Çünkü sadece HTTP servislerini yönetir.
    • C. Çünkü betik çalıştırır.
  3. advertised.listeners yanlışsa ne olur?
    • A. Client bağlanır fakat metadata adresi erişilemez.
    • B. Uygulama otomatik ölçeklenir.
