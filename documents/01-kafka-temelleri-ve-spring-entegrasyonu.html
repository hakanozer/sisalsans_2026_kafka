Partition, key ve group şeması

Key stratejisi: Sipariş event'inde orderId key'i aynı siparişe ait event'leri genellikle aynı partition'a yönlendirir ve partition içi sıralamayı korur. Null key ile dağıtım davranışı producer/client sürümüne ve partitioner'a bağlıdır. Key seçimi veri dağılımını da belirler: tek bir aşırı yoğun müşteri key'i hot partition yaratabilir.

2. Bir event'in producer'dan consumer'a yolculuğu

  1. Producer event oluşturur ve key belirler.
  2. Partitioner hedef partition'ı seçer; producer broker'a record gönderir.
  3. acks ayarıyla belirlenen onay koşulu sağlandığında send sonucu tamamlanır.
  4. Broker record'u partition log'una append eder ve offset atar.
  5. Consumer group partition assignment alır; consumer fetch eder, işler ve offset commit eder.
Dikkat: Producer future'ının başarılı tamamlanması ile iş veritabanı transaction'ının commit olması aynı transaction değildir. DB yazımı + Kafka publish atomikliği için transactional outbox gibi bir desen gerekir.

docker exec -it kafka-lab /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders.events --from-beginning --property print.key=true --property print.partition=true --property print.offset=true

Beklenen satırlar key, value, partition ve offset içerir. ORD-42 için iki event'in aynı partition'a gittiğini görün. Partitioner/hash detayları ve partition sayısının değiştirilmesinin routing etkisi için key policies'i ayrıca tartışın.

4. Spring Kafka: çalışan producer ve consumer parçaları

Aşağıdaki kodlar Kafka'ya özgü sınıflardır; controller, proje oluşturma ve REST iskeleti bu eğitim kapsamı dışındadır. Örnek Boot 4.1.1 kullanır, Maven/Gradle Spring Kafka sürümünü Boot dependency management'ten alır.

Bağımlılık

Boot parent/BOM mevcut kabul edilir; sürüm belirtilmez.

<dependency>
  <groupId>org.springframework.kafka</groupId>
  <artifactId>spring-kafka</artifactId>
</dependency>
dependencies {
    implementation("org.springframework.kafka:spring-kafka")
}

application.yml

spring:
  kafka:
    bootstrap-servers: localhost:9092
    producer:
      acks: all
      retries: 10
      properties:
        enable.idempotence: true
        max.in.flight.requests.per.connection: 5
      key-serializer: org.apache.kafka.common.serialization.StringSerializer
      value-serializer: org.springframework.kafka.support.serializer.JsonSerializer
    consumer:
      group-id: order-processor
      auto-offset-reset: earliest
      enable-auto-commit: false
      properties:
        isolation.level: read_committed
        spring.json.trusted.packages: com.example.orders
        spring.json.value.default.type: com.example.orders.OrderEvent
        spring.json.use.type.headers: false
      key-deserializer: org.apache.kafka.common.serialization.StringDeserializer
      value-deserializer: org.springframework.kafka.support.serializer.JsonDeserializer
    listener:
      ack-mode: manual

JsonSerializer/Deserializer class adları ve Spring JSON type header davranışı Spring Kafka sürümünde değişebilir. Bu sade örnek trusted package ve varsayılan event tipini açıkça belirler; uygulamada üretici/consumer kontratını kontrol edin, geniş wildcard trusted packages kullanmayın. Burada manual ack kullanıldığı için listener event işini tamamladıktan sonra Acknowledgment çağırır.

Event tipi ve producer

package com.example.orders;

import java.time.Instant;

public record OrderEvent(String orderId, String status, Instant occurredAt) {}

Record immutable event DTO'sudur. Event'e sonradan mutable entity veya secret alanları eklemeyin; payload bir dış sözleşmedir.

package com.example.orders;

import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.kafka.support.SendResult;
import org.springframework.stereotype.Service;
import java.time.Instant;
import java.util.concurrent.CompletableFuture;

@Service
public class OrderEventPublisher {
    private final KafkaTemplate<String, OrderEvent> kafkaTemplate;

    public OrderEventPublisher(KafkaTemplate<String, OrderEvent> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    public CompletableFuture<SendResult<String, OrderEvent>> publish(
            String orderId, String status) {
        var event = new OrderEvent(orderId, status, Instant.now());
        return kafkaTemplate.send("orders.events", orderId, event)
                .whenComplete((result, error) -> {
                    if (error != null) {
                        // Üretimde logger/metric/notification ile hatayı görünür kılın.
                        System.err.println("Kafka publish failed: " + error.getMessage());
                    } else {
                        var metadata = result.getRecordMetadata();
                        System.out.printf("Published topic=%s partition=%d offset=%d%n",
                                metadata.topic(), metadata.partition(), metadata.offset());
                    }
                });
    }
}

KafkaTemplate.send(topic,key,value) key'i sipariş kimliği yapar. Future sonucu log/metric üretir; başarısız publish'i başarı gibi saymayın. HTTP isteğini Kafka yanıtını bekleyerek sınırsız bloklamayın.

Topic, DLT ve retry yapılandırması

package com.example.orders;

import org.apache.kafka.clients.admin.NewTopic;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.kafka.config.TopicBuilder;

@Configuration
public class KafkaTopics {
    @Bean
    NewTopic ordersTopic() {
        return TopicBuilder.name("orders.events")
                .partitions(3).replicas(1).build();
    }

    @Bean
    NewTopic ordersDltTopic() {
        return TopicBuilder.name("orders.events.DLT")
                .partitions(3).replicas(1).build();
    }
}

Tek broker'da replicas(1) zorunlu lab sınırlamasıdır. Prod'da broker sayısı/replication ve ACL'yi platform ekibi belirlemelidir.

package com.example.orders;

import org.apache.kafka.common.TopicPartition;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.kafka.listener.DefaultErrorHandler;
import org.springframework.kafka.listener.DeadLetterPublishingRecoverer;
import org.springframework.util.backoff.FixedBackOff;

@Configuration
public class KafkaErrorConfiguration {
    @Bean
    DefaultErrorHandler kafkaErrorHandler(KafkaTemplate<Object, Object> template) {
        var recoverer = new DeadLetterPublishingRecoverer(
                template, (record, exception) ->
                new TopicPartition(record.topic() + ".DLT", record.partition()));
        return new DefaultErrorHandler(recoverer, new FixedBackOff(1_000L, 2L));
    }
}

Listener container factory'nin bu error handler'ı kullandığını uygulama sürümünüzde doğrulayın; Boot'un varsayılan factory'sine bean otomatik bağlanması Boot/Spring Kafka sürümüne bağlı olabilir. Gerekirse ConcurrentKafkaListenerContainerFactory bean'inde setCommonErrorHandler çağırın. DLT partition sayısını ana topic ile eşleştirin; retry edilemeyen poison event ve recoverer publish failure için alarm/operasyon prosedürü oluşturun.

Consumer ve header'lar

package com.example.orders;

import org.apache.kafka.clients.consumer.ConsumerRecord;
import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.kafka.support.Acknowledgment;
import org.springframework.stereotype.Component;

@Component
public class OrderEventConsumer {
    @KafkaListener(topics = "orders.events", groupId = "order-processor",
                   concurrency = "3")
    public void receive(ConsumerRecord<String, OrderEvent> record,
                        Acknowledgment acknowledgment) {
        var event = record.value();
        System.out.printf("key=%s partition=%d offset=%d timestamp=%d%n",
                record.key(), record.partition(), record.offset(), record.timestamp());
        System.out.printf("headers=%s order=%s status=%s%n",
                record.headers(), event.orderId(), event.status());
        // İş mantığı idempotent olmalı; listener hatasında ack etmeden exception fırlatın.
        acknowledgment.acknowledge();
    }
}

Bu explicit ack kodu için listener factory ack mode MANUAL veya MANUAL_IMMEDIATE olarak ayarlanmalıdır; record ack mode ile Acknowledgment verilmesi tutarlı değildir. Seçenek A: ack-mode: manual kullanın. Seçenek B: acknowledgment parametresini kaldırıp record listener tamamlanınca commit yaklaşımını seçin. Ack yalnızca iş etkisi güvenli biçimde tamamlandıktan sonra verilmelidir.

Önemli: Manual ack yalnızca iş etkisi güvenli biçimde tamamlandıktan sonra verilmelidir. Daha basit bir başlangıç alternatifi olarak acknowledgement parametresini kaldırıp ack-mode: record ile listener tamamlanınca commit yaklaşımını kullanın; transaction/DB işlemi ile offset atomikliği ayrıca tasarlanmalıdır.

Concurrency ve partition

concurrency=3 üç listener consumer thread'i açmayı ister; aynı group'ta en fazla üç partition bu örnekte paralel atanabilir. Consumer sayısını partition sayısından fazla açmak fayda sağlamaz ve thread/resource tüketir. Rebalance sırasında partition sahipliği değişebilir; handler hızlı dönmeli, uzun işleri kontrollü executor/outbox/iş kuyruğuna aktarın.

Otomatik ve manuel offset

enable.auto.commit=false consumer library'nin periyodik offset commit etmesini kapatır. Spring container seçilen ack mode'a göre commit yapar. Commit çok erken olursa event kaybı, çok geç olursa yeniden işleme (duplicate) ihtimali doğar. max.poll.records her poll'daki kayıt sayısını sınırlar; mesaj işleme süresi max.poll.interval.ms sınırını aşarsa consumer group rebalance olabilir. auto.offset.reset=earliest yalnızca group'ta geçerli committed offset yoksa uygulanır; her restart'ta baştan okutmaz.

5. Teslimat semantikleri: sınırlarıyla anlayalım

SemantikDavranışNe zaman / risk
At-most-onceOffset işten önce commit edilir; tekrar işlenmez, fakat arıza anında event kaybolabilir.Kaybın kabul edildiği telemetri örnekleri. Finansal işlemde uygun değildir.
At-least-onceOffset iş başarıyla tamamlandıktan sonra commit edilir; arızada event yeniden gelebilir.Sık tercih edilir. Consumer iş etkisi idempotent tasarlanmalı.
Exactly-onceKafka içindeki consume-process-produce ve offset commit akışı transaction/producer fencing ile atomik hale getirilebilir.Kafka'dan dış DB/e-posta/ödeme sistemi yan etkisini otomatik olarak exactly-once yapmaz. Dış sistemde idempotency veya outbox gerekir.

Producer güvenilirliği için acks=all, enable.idempotence=true, uygun retries ve max.in.flight.requests.per.connection kombinasyonunu desteklenen broker/client sürümünde kullanın. min.insync.replicas broker/topic policy'siyle birlikte değerlendirilir; tek broker lab'da 1'den yükseği yazımı engelleyebilir. Idempotent producer aynı producer session'ı içindeki retry duplicate riskini düşürür, iş event'inin iki kez publish edilmesini değil.

isolation.level=read_committed consumer'ın abort edilmiş transaction record'larını görmemesini sağlar; transaction kullanmayan basit producer için fark yaratmaz. Kafka transaction konusunu güvenilir mesajlaşma modülünde uygulayacağız.

6. Sıkı bağlı senkron akıştan gevşek bağlı event'lere

Sıkı bağlı akışın problemi: Order API sırayla Payment, Inventory ve Notification API'lerini çağırırsa her bağımlılığın erişilebilirliği ve yanıt süresi siparişin başarısını etkiler. Zaman aşımı sonrası belirsizlik, retry fırtınası ve zincirleme arıza oluşabilir.

Event yaklaşımı: Order servisi transaction/outbox sınırında OrderCreated event'i yayınlar. Payment, Inventory ve Notification kendi consumer group'larıyla bağımsız tüketir. Üretici consumer listesi bilmez; event contract'ı ortak entegrasyon yüzeyidir.

Bu gevşek bağ, iş akışının otomatik olarak tutarlı olduğu anlamına gelmez: eventual consistency, retry, duplicate, sıralama, telafi (saga) ve gözlemlenebilirlik tasarlanmalıdır.

7. Sık yapılan hatalar ve iyi uygulamalar

  • Topic genelinde total ordering var sanmak: sıralama partition içinde ve key politikasına bağlıdır.
  • Consumer group ID'yi servis instance'ı başına rastgele üretmek: her instance ayrı group olur ve her biri tüm event'leri alır. Aynı mantıksal uygulamanın replica'ları sabit group ID paylaşmalı.
  • earliest her açılışta başa döner sanmak: yalnız offset yoksa/uygun değilse kullanılır.
  • Başarılı Kafka ack'ini DB transaction başarısı sanmak: iki sistem ayrı transaction'dır.
  • Consumer'ı dış yan etki sonrası offset commit öncesi çökerse duplicate oluşabileceğini göz ardı etmek.
  • Partition sayısını iş yükü/ordering ihtiyacını anlamadan artırmak: key hash dağılımı değişebilir ve per-key sıralama garantisini zayıflatabilir.
  • Geniş JSON trusted package veya class header'larına koşulsuz güvenmek: payload tiplerini kontrollü allowlist edin.

İyi başlangıç: sabit group.id, key üzerinde aggregate ID, record başına idempotent handler, ölçülen lag, açık schema, retry limit ve DLT alarmı.

Mini alıştırma

  1. CLI producer ile aynı orderId key'ine CREATED ve PAID event'leri yazın. İki event'in partition ve offset'ini bulun.
  2. Consumer group ID'yi order-processor ile sabit tutup ikinci consumer instance başlatın. Partition'ların nasıl dağıldığını açıklayın.
  3. Topic'i 3 partition'dan 2'ye düşürme girişimi yapın veya neden mümkün olmadığını deneyle gösterin. Partition sayısını değiştirmenin key routing'e etkisini tartışın.
  4. Consumer iş etkisi tamamlanmadan offset commit edilirse hangi semantik oluşur? İşten sonra commit öncesi crash olursa?

Kontrol noktası: Aynı group içinde partition başına tek aktif owner; farklı group'lar topic'i bağımsız okuyabilir. Birçok Kafka admin API'si partition sayısını azaltmayı desteklemez.

Kısa özet

  • Kafka topic'i partition'lara bölünmüş kalıcı event log'udur; offset partition-local konumdur.
  • Key partition routing'ini ve partition içi ordering'i etkiler.
  • Consumer group paralellik ve bağımsız subscription sağlar.
  • Spring Kafka'da key'li KafkaTemplate, @KafkaListener, ack ve error handler bilinçli yapılandırılır.
  • At-least-once için duplicate ihtimalini idempotency ile yönetin; Kafka exactly-once dış DB yan etkilerini kapsamaz.

Kendini değerlendir

1. Kafka global topic sıralaması sağlar mı?

Hayır. Sıralama her partition içinde sağlanır.

2. Aynı group içindeki iki consumer aynı partition'ı eşzamanlı işler mi?

Normal assignment modelinde aynı group içinde bir partition aynı anda bir consumer üyeye atanır.

3. auto.offset.reset=earliest her restart'ta başa sarar mı?

Hayır. Group için kullanılabilir committed offset yoksa başlangıç konumunu belirler.

4. Idempotent producer consumer'ın DB'ye duplicate yazmasını engeller mi?

Hayır. Producer retry'larını kapsar; consumer side effect için idempotency gerekir.

5. Kafka transaction dış DB ile atomik commit sağlar mı?

Hayır. Kafka transaction Kafka record ve offset sınırında atomiklik sağlar; DB için outbox/CDC gibi desen gerekir.
