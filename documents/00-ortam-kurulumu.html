1. JDK 21 kurulumu ve kontrolü

Neden? Kafka broker'ı bu laboratuvarda container içinde çalışır; ancak Spring Boot uygulamaları ve bazı yerel araçlar host JDK'sını kullanacaktır. JDK'nın kurulu ve JAVA_HOME'un tutarlı olması sonraki uygulama adımlarını kolaylaştırır.

Nasıl? Eclipse Temurin'in resmi indirme sayfasından JDK 21 LTS paketini seçin. İşletim sisteminizin mimarisiyle eşleşen paketi indirin. Kurulum ekranı veya PATH tercihi sürüme göre değişebileceğinden dosya adını ezberlemeyin; release sayfasındaki güncel paketi kullanın.

  1. Temurin releases sayfasında Version 21 - LTS, Operating System Windows, Architecture x64 (ARM tabanlı Windows cihazda ARM64 paketi listeleniyorsa onu) ve Package Type JDK seçin; MSI indirip çalıştırın.
  2. Kurulum sihirbazında Set JAVA_HOME variable ve Add to PATH seçenekleri görünüyorsa seçin. Seçenekler görünmüyorsa kurulum sonrası aşağıdaki komutla mevcut terminal oturumu için ayarlayın.
  3. Yeni PowerShell açıp doğrulayın. Kalıcı ayarda kurulum klasörünün tam JDK dizinini Windows Environment Variables ekranında JAVA_HOME olarak tanımlayın ve %JAVA_HOME%\bin'i Path'e ekleyin.
$jdk = Get-ChildItem 'C:\Program Files\Eclipse Adoptium' -Directory |
  Where-Object Name -Like 'jdk-21*' |
  Sort-Object Name -Descending |
  Select-Object -First 1
if (-not $jdk) { throw 'JDK 21 bulunamadı; kurulum klasörünü kontrol edin.' }
$env:JAVA_HOME = $jdk.FullName
$env:Path = "$env:JAVA_HOME\bin;$env:Path"
java -version
Write-Output $env:JAVA_HOME

Beklenen: Java sürüm çıktısında 21 görünür. Bu PowerShell atamaları yalnızca mevcut terminal içindir; kalıcılık için Windows Environment Variables arayüzünü kullanın.

  1. Temurin releases sayfasında Version 21 - LTS, Operating System macOS ve Package Type JDK seçin. Apple Silicon (M serisi) Mac için aarch64 / ARM64, Intel Mac için x64 / x86_64 paketini indirin.
  2. PKG kurulum paketini açıp ekrandaki yönergeleri izleyin. Mimariden emin değilseniz Apple menüsü → About This Mac ekranındaki Chip/Processor bilgisini kontrol edin.
  3. Terminal (zsh) açıp Java'yı doğrulayın. Aşağıdaki JAVA_HOME tanımını ~/.zshrc dosyasına ekleyerek yeni terminal oturumlarında da kullanın.
/usr/libexec/java_home -V
echo 'export JAVA_HOME=$(/usr/libexec/java_home -v 21)' >> ~/.zshrc
echo 'export PATH="$JAVA_HOME/bin:$PATH"' >> ~/.zshrc
source ~/.zshrc
java -version
echo "$JAVA_HOME"

Beklenen: sürüm çıktısında 21 ve JAVA_HOME için Temurin JDK dizini görünür. Mac'te Apple Silicon ve Intel için aynı kullanım komutları geçerlidir; indirilen paket mimarisi farklıdır.

Kontrol noktası: java -version JDK 21 (veya uyumlu başka bir JDK 17+) göstermeli. JRE değil, JDK kurduğunuzu doğrulayın.

3. Container engine: dockerd (Moby) mi, containerd mi?

dockerd (Moby)

Docker Engine API'sini ve docker CLI'yi sağlar. Pek çok Spring Boot geliştirme akışı ve Docker Compose örneğiyle doğrudan uyumludur. Bu eğitimde bunu seçiyoruz.

containerd

Kubernetes ekosisteminde kullanılan container runtime'dır. Rancher Desktop, bunun yanında nerdctl CLI sunar. Docker CLI/Compose bekleyen araçlarla ek uyarlama gerekir. Docker engine ile aynı şey değildir.

Kubernetes, container runtime değildir; container'ları yöneten ayrı bir orkestrasyon katmanıdır. Kafka'yı burada Docker Compose ile çalıştıracağımız için Kubernetes'i etkinleştirmek gerekmiyor.

Runtime'ı containerd seçtiyseniz ve nerdctl kuruluysa, kontrol için:

nerdctl version
nerdctl info
nerdctl compose version

Containerd seçeneğinde bu dokümandaki Compose komutlarını nerdctl compose ile çalıştırmayı deneyebilirsiniz. Ancak bu eğitimde verilen varsayılan yol ve kontroller dockerd (Moby) + docker compose içindir. Komut bulunamazsa container engine ayarını dockerd'e alıp Rancher Desktop'ı yeniden başlatın.

Kurulum doğrulama: Hata almadan docker version, docker compose version ve docker info çalışmadan Kafka'yı başlatmayın. İlk image indirme işlemi registry erişimi nedeniyle zaman alabilir.

4. Kafka'yı KRaft modunda Docker Compose ile başlatma

Neden? Kafka 4.x laboratuvarında ZooKeeper kullanmadan KRaft metadata yönetimini göreceğiz. Tek broker/controller container'ı kurulumu kolaylaştırır; fakat yedeklilik sağlamaz.

Nasıl? Aşağıdaki dosyayı docker-compose.yml adıyla yeni bir klasöre kaydedin. İmaj sürümü sabitlenmiştir; Compose dosyasını çalıştırdığınız dizin proje dizini olacaktır.

Dosyayı oluşturma

PowerShell'de çalışma klasörünü oluşturup içine geçin. Sonraki komut, bir sonraki bölümdeki YAML içeriğini docker-compose.yml olarak kaydeder.

New-Item -ItemType Directory -Force -Path "$HOME\kafka-lab" | Out-Null
Set-Location "$HOME\kafka-lab"

Terminal'de çalışma klasörünü oluşturup içine geçin. Sonraki adımda YAML içeriğini docker-compose.yml dosyasına kaydedin.

mkdir -p "$HOME/kafka-lab"
cd "$HOME/kafka-lab"

Bu tam Compose içeriğini dosyaya kaydedin:

    container_name: kafka-lab

5. Host makineden Kafka'ya bağlantı: listener ve advertised listener

Neden? Kafka istemcisi bootstrap adresine ilk bağlantıyı kurduktan sonra broker metadata'sını alır ve broker'ın ilan ettiği adrese tekrar bağlanır. Container içindeki DNS adı host işletim sisteminde çözümlenmeyebilir; yanlış advertised adresi, başlangıç bağlantısı kurulsa bile istemciyi koparabilir.

Nasıl? Bu Compose yapılandırmasında dış uygulama ve terminal araçları localhost:9092 ile erişir. Compose ağındaki diğer container'lar broker:19092 kullanmalıdır. KRaft controller trafiği 29093'te kalır.

Bağlantı akışı:
  1. Client bootstrap adresiyle metadata ister.
  2. Broker, bağlantının geldiği listener için ilan edilen broker adresini döndürür.
  3. Client bu adrese yeniden bağlanır. Host dışındaki bir makine için localhost o makinenin kendisini ifade eder; bu yüzden bu örnek yalnızca host üzerindeki istemciler içindir.

Önemli ayarlar: listeners bind edilen interface ve portları; advertised.listeners client'a bildirilen DNS adı/portu; Compose ports ise host-container port yayınlamasını belirler. Bu üçü birbirinin yerine geçmez.

Windows/macOS'ta Spring Boot host'ta çalışırken spring.kafka.bootstrap-servers=localhost:9092 (veya ilgili client bootstrap servers) kullanın. Spring uygulamasını aynı Compose ağına container olarak koyduğunuzda broker:19092 kullanın. Host uygulamasından broker:19092 kullanmayın; host bu container DNS adını genellikle çözemez.

6. Topic ve event'lerle uçtan uca CLI testi

Neden? Spring koduna geçmeden önce broker'ın erişilebilir, topic'in yazılabilir ve mesajın okunabilir olduğunu bağımsız olarak doğruluyoruz.

Nasıl? Komutları Compose dosyasının olduğu klasörde Windows PowerShell veya macOS Terminal'den çalıştırın. Kafka CLI komutları container'ın içindeki Apache dağıtımını kullanır.

Broker durumunu ve listener portunu kontrol edin

docker compose ps
docker compose logs --tail 80 broker

Host'tan port erişim testi:

Test-NetConnection localhost -Port 9092

Beklenen: TcpTestSucceeded : True.

nc -vz localhost 9092

Beklenen: succeeded benzeri TCP bağlantı başarılı mesajı.

Topic oluşturma, listeleme ve detayını görme

docker exec kafka-lab /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --if-not-exists --topic orders.lab --partitions 1 --replication-factor 1
docker exec kafka-lab /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list
docker exec kafka-lab /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic orders.lab

Bu örneklerde komutlar tek satır tutulmuştur; aynı biçim Windows PowerShell ve macOS zsh'de çalışır.

Beklenen describe çıktısında Topic: orders.lab, PartitionCount: 1, ReplicationFactor: 1 ve partition 0 için leader görünür. Tek replica nedeniyle bu ayarlar sadece lab içindir.

Console producer ile event yazın

Bu komut terminali interaktif moda geçirir. İki satırı girin, ardından Ctrl+C ile producer'ı kapatın.

docker exec -it kafka-lab /opt/kafka/bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic orders.lab
{"orderId":"ORD-1001","status":"CREATED"}
{"orderId":"ORD-1002","status":"CREATED"}

Her satır ayrı bir Kafka record olur. Bu testte key vermedik; partition/key ilişkisini Part 1 dokümanında inceleyeceğiz.

Console consumer ile event okuyun

Yeni terminal açıp aşağıdaki komutu çalıştırın. --from-beginning topic'in mevcut başlangıcından okumayı ister. Çıkmak için Ctrl+C.

docker exec -it kafka-lab /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders.lab --from-beginning

Beklenen: ORD-1001 ve ORD-1002 kayıtlarının JSON metinleri. Sonuç görülmüyorsa producer'ın aynı topic'e yazdığını ve consumer'ın doğru broker'a bağlandığını kontrol edin.

Host makinedeki Kafka CLI ile test (isteğe bağlı)

Kafka binary distribution'ın CLI araçlarını da kullanabilirsiniz. İmaj içindeki CLI yukarıdaki adımlar için yeterli olduğundan bu adım zorunlu değildir. Kafka'nın resmi indirme sayfasından uyumlu binary distribution'ı indirin. Windows'ta bin\windows\kafka-topics.bat, macOS'ta bin/kafka-topics.sh kullanın. Uygulama için JDK 17+ ve localhost:9092 gerekir.

.\bin\windows\kafka-topics.bat --bootstrap-server localhost:9092 --list
.\bin\windows\kafka-console-consumer.bat --bootstrap-server localhost:9092 --topic orders.lab --from-beginning
./bin/kafka-topics.sh --bootstrap-server localhost:9092 --list
./bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders.lab --from-beginning
Başarı ölçütü: Compose service Up; host port 9092 reachable; orders.lab listeleniyor; topic description bir leader gösteriyor; consumer yazdığınız iki JSON satırını okuyor.

7. Ortamı durdurma, temizleme ve sıfırlama

Geçici durdurma, broker container'ını durdurur ama container ve volume verisini korur:

docker compose stop
docker compose start
docker compose ps

Container'ları kaldırıp volume'daki Kafka verisini korumak için:

docker compose down

Tam laboratuvar sıfırlaması topic'leri, event'leri ve KRaft metadata'sını içeren kafka-data volume'unu da siler. Bu işlem geri alınamaz; yalnızca lab verisini kaybetmeyi kabul ediyorsanız çalıştırın:

docker compose down -v
Dikkat: -v volume siler. Gerçek veya korunması gereken bir Kafka volume'unda çalıştırmayın. Sıfırlama sonrası tekrar docker compose up -d ile boş broker başlar.

Rancher Desktop'ı kapatmak için uygulamanın menüsünden Quit seçin. Factory Reset yalnızca tüm Rancher Desktop kümesini/ayarlarını temizlemek istediğinizde kullanılır; bu Kafka lab'ını sıfırlamak için gerekli değildir. Uygulamayı kaldırmak, volume verisinin de silindiği anlamına gelmez.

Mini alıştırma

  1. orders.lab topic'ini 3 partition ile oluşturun. Neden replication factor 1 kalmalı?
  2. İki yeni event gönderin; consumer'ı --from-beginning olmadan çalıştırın. Gözleminiz nedir?
  3. Host'ta çalışan bir istemci için hangi bootstrap adresini, Compose ağı içindeki istemci için hangisini kullanırsınız? İki adresin de neden gerekli olduğunu açıklayın.
  4. Topic'in partition sayısını ve leader bilgisini kafka-topics --describe çıktısından bulun.

Yönlendirme: İlk sorunun komutu --partitions 3 --replication-factor 1 parametrelerini kullanır. Tek broker olduğundan replica factor 1'i aşamaz. İkinci soruda yeni consumer group ilk kez başlıyorsa varsayılan başlangıç davranışı ile önceden yazılmış event'ler okunmayabilir; sonraki modüllerde auto.offset.reset ve consumer group offset'lerini inceleyeceğiz.

  • Rancher Desktop dockerd/Moby runtime ile kuruldu; bu laboratuvarda Kubernetes kapalı.
  • Resmi apache/kafka:4.3.1 imajı tek broker/controller olarak KRaft modunda çalıştırıldı.

Kendini değerlendir

Önce soruları yanıtlayın, sonra her cevabı açıp kontrol edin.

1. Bu lab'da neden dockerd (Moby) seçiyoruz?

Çünkü verilen uygulama adımları ve Compose dosyası Docker CLI/API'sini kullanır; docker compose ile en doğrudan çalışır. containerd de çalıştırabilir ancak nerdctl ile komut farklılıkları olabilir.

2. KRaft kurulumunda ZooKeeper var mı?

Hayır. KRaft, Kafka'nın metadata/quorum yönetimini Kafka controller'larıyla yapar. Bu tek düğümlü lab'da broker ve controller rolleri aynı process/container'dadır.

3. Host'taki Spring uygulaması hangi adrese bağlanmalı?

localhost:9092. Compose ağı içindeki uygulama ise broker:19092 kullanır. İlan edilen adres, istemcinin çalıştığı network'ten erişilebilir olmalıdır.

4. docker compose down ile docker compose down -v arasındaki fark nedir?

down container ve network'ü kaldırır, yönetilen volume verisini varsayılan olarak korur. down -v volume'u da silerek Kafka event ve metadata verisini kalıcı olarak kaldırır.

5. Bu tek broker lab'ı neden production için uygun değildir?

Tek replica, tek broker ve PLAINTEXT nedeniyle broker arızasına karşı yedeklilik, uygun güvenlik ve production dayanıklılığı sağlamaz. Üretimde çok broker, replication, TLS/authentication/ACL, izleme ve işletim politikaları gerekir.
