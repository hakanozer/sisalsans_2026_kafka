1. Neden schema registry; nasıl çalışır?

Registry schema'yı merkezi kaydeder, subject/version yönetir ve yeni schema'nın compatibility policy'sini doğrular. Producer serializer schema'yı kaydedip mesajda schema ID taşır; consumer deserializer ID ile schema'yı alıp payload'ı çözer. Registry broker değildir, event payload'larını saklamaz; Kafka record key/value byte'larını saklar.

FormatAvantajDikkat
AvroCompact binary; schema-first ve code generation güçlü.Defaults/union/evolution kurallarını doğru modelleyin; raw bytes console çıktısı okunmaz.
ProtobufBinary, güçlü code generation, tag number ile evolution.Field number silinince re-use etmeyin; reserved num/name kullanın.
JSON Schemaİnsan tarafından okunabilir JSON ve yaygın ekosistem.Payload daha büyük; schema dialect ve optional/default/union yorumları değişebilir.

Subject naming strategy kritik: varsayılan TopicNameStrategy genellikle topic-value subject'i kullanır; record bazlı paylaşımda RecordNameStrategy gerekebilir. Producer ve consumer aynı subject stratejisinde anlaşmalıdır.

2. Schema evolution: backward/forward/full

“Uyumluluk” deploy sırasındaki eski/yeni producer ve consumer kombinasyonunun okuyup işleyebilmesidir. Formatın syntactic validity'si tek başına business compatibility değildir.

PolicyYeni reader ile eski data?Eski reader ile yeni data?Örnek rollout
BackwardEvet (yeni reader eski writer)Garanti değilConsumer'ları yeni sürüme geçirin, ardından yeni producer.
ForwardGaranti değilEvet (eski reader yeni writer)Producer önce yeni alanı yazar; eski consumer toleranslı kalır.
FullEvetEvetİki yönde uyumluluk gereken gradual rollout.

Registry compatibility kontrolü schema resolution kurallarına göre yapılır; semantic meaning (ör. kuruş → lira) doğrulayamaz. Safe değişiklik örnekleri format ve policy'ye göre farklıdır: Avro'da yeni field'a default eklemek çoğunlukla backward-safe; Protobuf'ta field number'ı korumak gerekir. Required field ekleme, rename, enum removal, unit/meaning change kırılma yaratabilir.

Invoke-RestMethod http://localhost:8081/config/orders-value
Invoke-RestMethod http://localhost:8081/subjects/orders-value/versions
$payload = '{"compatibility":"BACKWARD"}'
Invoke-RestMethod -Method Put -Uri http://localhost:8081/config/orders-value -ContentType "application/vnd.schemaregistry.v1+json" -Body $payload
curl -s http://localhost:8081/config/orders-value
curl -s http://localhost:8081/subjects/orders-value/versions
curl -X PUT -H 'Content-Type: application/vnd.schemaregistry.v1+json' --data '{"compatibility":"BACKWARD"}' http://localhost:8081/config/orders-value

Beklenen: config JSON veya version listesi, örneğin [1,2]. Compatibility mode'u production subject'larında gelişigüzel değiştirmeyin; global ve subject-level override etkisini kontrol edin.

3. Rancher Desktop'ta Schema Registry'yi çalıştırma

İki OS'ta adımlar aynı: 00'da kullandığınız docker-compose.yml klasörüne geçin ve broker'ı çalışır bırakın. Dosyanın services: altına schema-registry servisini ekleyin. volumes: bölümünü değiştirmeyin.

  schema-registry:
    image: confluentinc/cp-schema-registry:8.3.2
    container_name: kafka-schema-registry
    depends_on:
      - broker
    ports:
      - "8081:8081"
    environment:
      SCHEMA_REGISTRY_HOST_NAME: schema-registry
      SCHEMA_REGISTRY_LISTENERS: http://0.0.0.0:8081
      SCHEMA_REGISTRY_KAFKASTORE_BOOTSTRAP_SERVERS: PLAINTEXT://broker:19092
      SCHEMA_REGISTRY_KAFKASTORE_TOPIC_REPLICATION_FACTOR: 1

Windows PowerShell ve macOS zsh için çalışma/başlatma komutları:

Set-Location "$HOME\kafka-lab"
docker compose config
docker compose up -d schema-registry
docker compose logs -f schema-registry

Ctrl+C yalnızca log takibini keser.

cd "$HOME/kafka-lab"
docker compose config
docker compose up -d schema-registry
docker compose logs -f schema-registry

Ctrl+C yalnızca log takibini keser.

Registry bir metadata topic'i olan _schemas'ı Kafka'ya yazar; tek broker lab nedeniyle replication factor 1 olarak ayarlanır. depends_on yalnızca container start sırasını etkiler, servisin hazır olduğunu garanti etmez. Loglarda HTTP listener hazır olana kadar bekleyin.

API hazır mı?

Invoke-RestMethod http://localhost:8081/subjects

İlk kullanımda boş subject listesi beklenir.

curl -i http://localhost:8081/subjects

HTTP 200 ve boş liste [] beklenir.

Lab güvenliği: Bu config HTTP/PLAINTEXT ve auth'suzdur. Yalnızca local eğitim ağı için. Üretimde TLS, authentication, ACL/network policy, registry persistence/HA, secret yönetimi ve audited schema changes gerekir.

4. Spring Kafka + Avro serializer

Avro class'ları .avsc schema'dan build sırasında generate edilir veya GenericRecord kullanılır. Aşağıdaki dependencies için Confluent Maven repository ve version alignment gerekir; Boot dependency management Spring Kafka'yı yönetir, Confluent serializer kendi BOM/version'ıyla uyumlu olmalıdır.

Maven

Confluent artifact'ları için Maven repository tanımı gerekebilir (kurum içi artifact mirror kullanıyorsanız mirror'ı tercih edin):

<repositories>
  <repository>
    <id>confluent</id>
    <url>https://packages.confluent.io/maven/</url>
  </repository>
</repositories>

<dependency>
  <groupId>org.springframework.kafka</groupId>
  <artifactId>spring-kafka</artifactId>
</dependency>
<dependency>
  <groupId>io.confluent</groupId>
  <artifactId>kafka-avro-serializer</artifactId>
  <version>8.3.2</version>
</dependency>
<dependency>
  <groupId>org.apache.avro</groupId>
  <artifactId>avro</artifactId>
  <version>1.12.0</version>
</dependency>

<build>
  <plugins>
    <plugin>
      <groupId>org.apache.avro</groupId>
      <artifactId>avro-maven-plugin</artifactId>
      <version>1.12.0</version>
      <executions>
        <execution>
          <phase>generate-sources</phase>
          <goals><goal>schema</goal></goals>
        </execution>
      </executions>
    </plugin>
  </plugins>
</build>

Confluent Maven repository istenebilir; dependency resolution kurum mirror'unda başarısızsa repository'yi kontrollü ekleyin ve version compatibility resmi Confluent release matrix ile doğrulayın. Avro library versiyonunu Confluent serializer ile bağımsızca yükseltmeyin. Schema dosyasını src/main/avro/OrderCreated.avsc altında tutun; Avro Maven plugin bu varsayılan konumdan Java tipi üretir.

Avro schema dosyası

{
  "type": "record",
  "name": "OrderCreated",
  "namespace": "com.example.orders",
  "fields": [
    {"name": "orderId", "type": "string"},
    {"name": "amountCents", "type": "long"},
    {"name": "currency", "type": "string"}
  ]
}

application.yml

spring:
  kafka:
    bootstrap-servers: localhost:9092
    properties:
      schema.registry.url: http://localhost:8081
      specific.avro.reader: true
    producer:
      acks: all
      properties:
        enable.idempotence: true
      key-serializer: org.apache.kafka.common.serialization.StringSerializer
      value-serializer: io.confluent.kafka.serializers.KafkaAvroSerializer
    consumer:
      group-id: order-avro-reader
      auto-offset-reset: earliest
      enable-auto-commit: false
      key-deserializer: org.apache.kafka.common.serialization.StringDeserializer
      value-deserializer: io.confluent.kafka.serializers.KafkaAvroDeserializer

specific.avro.reader=true generated SpecificRecord class gerektirir. GenericRecord tüketiyorsanız ayarı kaldırın. Production Registry URL/auth/TLS secret'larını source control'e yazmayın.

Record oluşturup gönderme (generated class varsayımı)

@Service
public class AvroOrderPublisher {
    private final KafkaTemplate<String, OrderCreated> template;

    public AvroOrderPublisher(KafkaTemplate<String, OrderCreated> template) {
        this.template = template;
    }

    public CompletableFuture<SendResult<String, OrderCreated>> send(
            String orderId, long amountCents) {
        var event = OrderCreated.newBuilder()
                .setOrderId(orderId)
                .setAmountCents(amountCents)
                .setCurrency("TRY")
                .build();
        return template.send("orders.avro", orderId, event);
    }
}

Generated Avro Java class build plugin'in package/name alanlarına göre üretilir; schema formatını API contract olarak review edin. Key orderId; Avro value registry serializer üzerinden serialize olur. Future failure'ını log/metric ile görünür yapın.

CLI ile schema doğrulama ve gözlem

Örnek Avro schema'yı Registry'ye kaydedip subjects listesini kontrol edin. Windows PowerShell'de schema dosyasından request body oluşturun:

$schema = Get-Content .\src\main\avro\OrderCreated.avsc -Raw | ConvertTo-Json -Compress
$body = @{ schema = $schema; schemaType = "AVRO" } | ConvertTo-Json -Compress
Invoke-RestMethod -Method Post -Uri http://localhost:8081/subjects/orders.avro-value/versions -ContentType "application/vnd.schemaregistry.v1+json" -Body $body
Invoke-RestMethod http://localhost:8081/subjects
curl -i -X POST http://localhost:8081/subjects/orders.avro-value/versions -H 'Content-Type: application/vnd.schemaregistry.v1+json' --data '{"schema":"{\"type\":\"record\",\"name\":\"OrderCreated\",\"namespace\":\"com.example.orders\",\"fields\":[{\"name\":\"orderId\",\"type\":\"string\"},{\"name\":\"amountCents\",\"type\":\"long\"},{\"name\":\"currency\",\"type\":\"string\"}]}","schemaType":"AVRO"}'
curl -s http://localhost:8081/subjects

Başarılı kayıt yanıtı schema id döndürür; subject listesinde orders.avro-value görünmelidir. Ardından topic'e event'i Spring producer ile yayınlayıp Kafka topic'i kontrol edin. Avro wire payload console consumer'da okunabilir JSON görünmek zorunda değildir.

docker exec kafka-lab /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list
docker exec kafka-lab /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list
docker exec kafka-lab /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders.avro --from-beginning --property print.key=true

Beklenen: Registry'de orders.avro-value (default TopicNameStrategy) gibi subject; Kafka CLI'de topic ve serialized bytes. Gerçek payload decode etmek için serializer-aware Spring consumer veya registry destekli CLI kullanın.

Sık yapılan hatalar ve iyi uygulamalar

  • Schema Registry'yi broker zannetmek; Registry unavailable olunca serializer config/cache davranışı ayrıca değerlendirilmelidir.
  • Uyumluluk ayarı schema syntax'ını kontrol ediyor sanmak; business semantic değişikliklerini ekip review/test etmelidir.
  • Breaking change'i tüm consumer'lar deploy olmadan yayınlamak.
  • Avro default alanının “producer için otomatik değer” olduğunu sanmak: reader/writer schema resolution bağlamında anlamı vardır.
  • Protobuf field number'ını yeniden kullanmak veya Avro field rename'i alias/default stratejisi olmadan yapmak.
  • Subject naming strategy'yi servisler arasında farklı ayarlamak; topic-level schema lifecycle sahipliği belirsiz bırakmak.
  • Schema içinden gereksiz PII'yi uzun süreli Kafka retention'a taşımak.
  • Kafka console consumer ile Avro bytes'ı JSON gibi okumaya çalışmak.

Öneri: contract tests, consumer-driven compatibility checks, staged rollout, schema owner, deprecation window, event example fixtures ve registry audit süreçleri.

Mini alıştırma

  1. OrderCreated Avro schema'ya optional couponCode alanı ekleyin. Eski data'yı yeni reader okurken gereken default/union davranışını belirleyin.
  2. amountCents'i decimal string'e çevirmeyi breaking change olarak değerlendirin; migration/versioning planı önerin.
  3. REST API ile subject compatibility ayarını okuyup bir schema version'ı listeleyin.
  4. Spring producer ile bir record gönderip Registry subject'i ve Kafka topic'i gözlemleyin.

Kontrol noktası: Yeni consumer eski message'i okuyabiliyor mu ve eski consumer yeni message'i okuyabiliyor mu? Bu iki sorunun cevabı compatibility yönünü belirler.

Kısa özet

  • Registry schema metadata/compatibility sağlar; event bytes Kafka'dadır.
  • Serializer schema ID ile wire format'ı üretir; consumer registry'den schema edinir.
  • Avro, Protobuf ve JSON Schema'nın evolution kuralları farklıdır.
  • Subject strategy, version compatibility ve rollout sırası API sözleşmesinin parçasıdır.

Kendini değerlendir

1. Schema Registry event payload'larını saklar mı?

Hayır; schema ve versiyon metadata'sını saklar, payload Kafka'da tutulur.

2. Backward compatibility hangi yönü hedefler?

Yeni reader'ın eski writer schema ile yazılmış data'yı okuyabilmesini.

3. Protobuf field number neden korunmalı?

Wire compatibility için numara alan kimliğidir; silinen numara yeniden kullanılırsa yanlış decode riski oluşabilir.

4. Console consumer Avro payload'ı neden okunur JSON göstermeyebilir?

Avro wire format binary data ve schema ID içerir; registry-aware deserializer gerekir.

5. Registry availability neden producer başarısını etkileyebilir?

Schema serializer ilk/ilgili schema için registry'ye erişmek zorunda kalabilir; cache ve failure davranışı serializer config'e bağlıdır.
