Kafka Connect ve Stream Processing

1. Kafka Connect: source, sink, worker, task

Neden? Her veri kaynağı/ hedef için tekrar tekrar bespoke producer/consumer yazıp offset, retry ve lifecycle yönetmek maliyetlidir.

Nasıl? Connect worker connector plugin'lerini çalıştırır; connector işi task'lara böler. Source dış sistem → Kafka, sink Kafka → dış sistem yönündedir. Converter wire format'ını; SMT (Single Message Transform) basit record mapping'i sağlar. Büyük iş dönüşümü için SMT kullanmayın.

ConnectorJDBC/DB/HTTP gibi sistem bağlantısıPlugin her worker node'da aynı classpath/version ile olmalı.

2. CDC ve Debezium

Neden? Uygulama DB'sinden Kafka'ya güvenilir değişiklik aktarımı, polling sorgularının DB'yi yüklemesini ve her servisin dual-write yapmasını önlemeye yardımcı olur.

Nasıl? Debezium source connector DB snapshot alır, ardından transaction log/WAL'daki row değişikliklerini takip edip Kafka topic'lerine yayar. Snapshot ve log akışı, offset/LSN, schema history, DB privileges, replication slot/retention birlikte yönetilmelidir. CDC row-level change'dir; domain event değildir. Domain event üretmek için semantic mapping/outbox gerekir.

Güvenlik: Aşağıdaki örnek yalnızca local lab'dır. DB parolası demo, port 5432 host'a yayınlanmıyor. Production'da least-privilege CDC user, secrets manager, WAL disk alarmı, TLS, retention ve restore prosedürü gerekir.

3. Kafka Streams

Neden? Event'ler üzerinde stateful aggregation, join, window ve materialized state'i Java service içinde yapmak için.

Nasıl? StreamsBuilder topology kurar; Kafka Streams client input topic'leri tüketir, state store/changelog ile state'i kurtarır ve output topic'ine yazar. application.id consumer group ve internal state topic isimlerini belirler. EOS v2, processing guarantees ayarıyla Kafka input/output/offset akışını transaction'a alabilir; external API yan etkisini kapsamaz.

Spring Kafka Streams yapılandırması (string demo)

spring:
  kafka:
    bootstrap-servers: localhost:9092
    streams:
      application-id: order-status-normalizer
      properties:
        processing.guarantee: exactly_once_v2
        commit.interval.ms: 1000

Exactly-once lab tek broker ve RF=1 ile production dayanıklılık garantisi değildir. Kafka Streams config/internal topic replication policy'lerini multi-broker production topology'ye göre ayarlayın.

@Configuration
@EnableKafkaStreams
class OrderTopology {
    @Bean
    KStream<String, String> normalize(StreamsBuilder builder) {
        var input = builder.stream("orders.raw");
        input.mapValues(String::toUpperCase)
             .to("orders.normalized");
        return input;
    }
}

Imports: org.apache.kafka.streams.StreamsBuilder, org.apache.kafka.streams.kstream.KStream, Spring @EnableKafkaStreams. Dependency org.springframework.kafka:spring-kafka ve org.apache.kafka:kafka-streams; Kafka Streams dependency sürümünü Spring Boot/Spring Kafka BOM matrisiyle eşleştirin, arbitrary version override etmeyin.

4. ksqlDB

Neden? SQL bilen ekiplerin stream-table, filter, projection, windowed aggregate gibi işleri JVM service yazmadan tanımlamasını sağlar.

Nasıl? ksqlDB server Kafka cluster'a bağlanır; SQL statement persistent query olarak topic okur/yazar. Schema Registry integration opsiyoneldir fakat production schema governance ile birlikte kullanılmalıdır. ksqlDB image availability, license ve lifecycle statüsünü kurumsal platformda teyit edin; self-managed dağıtım Confluent bileşenidir.

CREATE STREAM order_events (
  orderId VARCHAR,
  status VARCHAR
) WITH (
  KAFKA_TOPIC='orders.sql.lab',
  VALUE_FORMAT='JSON'
);

CREATE STREAM created_orders AS
  SELECT orderId, status
  FROM order_events
  WHERE status = 'CREATED'
  EMIT CHANGES;

SQL syntax/format desteği ksqlDB version'ına göre değişebilir. Stream'e veri gönderip SELECT * FROM created_orders EMIT CHANGES; ile çıktıyı gözleyin.

5. Rancher Desktop: Connect + Debezium + PostgreSQL + ksqlDB

00'daki Compose dosyasını kullanın. services: altına aşağıdaki servisleri ekleyin. Dosyanın en altındaki mevcut volumes: bölümünü yeni postgres-data volume'unu da içerecek şekilde güncelleyin; aynı seviyede iki volumes: anahtarı bırakmayın. Compose iç DNS içinde broker adresi broker:19092 olmalı.

  postgres:
    image: postgres:17.6
    container_name: lab-postgres
    environment:
      POSTGRES_DB: lab
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: lab-only-password
    command: ["postgres", "-c", "wal_level=logical"]
    volumes:
      - postgres-data:/var/lib/postgresql/data

  connect:
    image: quay.io/debezium/connect:3.7
    container_name: kafka-connect
    depends_on:
      - broker
      - postgres
    ports:
      - "8083:8083"
    environment:
      BOOTSTRAP_SERVERS: broker:19092
      GROUP_ID: "1"
      CONFIG_STORAGE_TOPIC: connect_configs
      CONFIG_STORAGE_REPLICATION_FACTOR: "1"
      OFFSET_STORAGE_TOPIC: connect_offsets
      OFFSET_STORAGE_REPLICATION_FACTOR: "1"
      STATUS_STORAGE_TOPIC: connect_statuses
      STATUS_STORAGE_REPLICATION_FACTOR: "1"
      REST_ADVERTISED_HOST_NAME: connect
      KEY_CONVERTER: org.apache.kafka.connect.json.JsonConverter
      VALUE_CONVERTER: org.apache.kafka.connect.json.JsonConverter
      VALUE_CONVERTER_SCHEMAS_ENABLE: "false"

  ksqldb-server:
    image: confluentinc/cp-ksqldb-server:8.3.2
    container_name: kafka-ksqldb
    depends_on:
      - broker

      KSQL_LISTENERS: http://0.0.0.0:8088

      KSQL_KSQL_LOGGING_PROCESSING_TOPIC_REPLICATION_FACTOR: "1"
      KSQL_KSQL_LOGGING_PROCESSING_STREAM_AUTO_CREATE: "true"

  ksqldb-cli:
    image: confluentinc/cp-ksqldb-server:8.3.2

volumes:
  kafka-data:
  postgres-data:

Debezium project release 3.7.0.Final is current; the Quay.io image tag used here is the confirmed 3.7 release-series tag. Confluent components 8.3.2 are from the official quickstart. ksqlDB stream processing denemesi

Compose CLI container'ına interaktif bağlanın. Önce CLI komutuyla bağlanın ve orders.sql.lab topic'ini oluşturun. İki OS'ta da aşağıdaki komutlar aynıdır:

docker exec kafka-lab /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --if-not-exists --topic orders.sql.lab --partitions 1 --replication-factor 1
docker compose exec -it ksqldb-cli ksql http://ksqldb-server:8088

Yeni terminalden console producer'ı başlatıp JSON record girin; örneğin {"orderId":"O-9","status":"CREATED"}. Ctrl+C ile producer'dan çıkın, ardından ksqlDB prompt'una SQL'i girin:

docker exec -it kafka-lab /opt/kafka/bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic orders.sql.lab
CREATE STREAM order_events (
  orderId VARCHAR KEY,
  status VARCHAR
) WITH (KAFKA_TOPIC='orders.sql.lab', VALUE_FORMAT='JSON');

CREATE STREAM created_orders AS
  SELECT orderId, status FROM order_events
  WHERE status = 'CREATED' EMIT CHANGES;

SELECT * FROM created_orders EMIT CHANGES;

Beklenen: input event, persistent query tarafından filtrelenir ve result stream'de görülür. Schema-registry / structured JSON versiyonunda schema ve format config'i ayrıca verin.

Operasyonel gözlemler, hatalar ve iyi uygulamalar

  • GET /connectors, /status, worker logs; Connect offset/config/status internal topics'i izleyin.
  • Debezium PostgreSQL replication slot WAL biriktirebilir; connector kesilirse disk dolabilir. WAL retention/slot lag alert zorunlu.
  • Source snapshot'i production'da yük oluşturabilir; table include list, snapshot mode ve incremental snapshot planlanmalı.
  • Connect REST API'yi internete açmayın; credentials TLS/auth, network segmentation ve admin ACL ile korunmalı.
  • Converter JSON Schema yoksa schema'sız event üretir; production schema governance ile uyumlu converter/Registry seçin.
  • Kafka Streams state store/changelog disk kullanır; standby replicas, task assignment, EOS, state restore ve local storage planlanmalı.
  • ksqlDB query'leri Kafka Streams application gibi internal topics ve state oluşturabilir; persistent query adlandırma ve lifecycle yönetilmeli.
  • CLI record'larında JSON bir envelope ise ksqlDB'de alan path/schema modellemesi gerekir; nested Debezium JSON'u flat row sanmayın.

Lab'ı durdurmak için docker compose stop connect postgres ksqldb-server; volume dahil sıfırlamak isterseniz docker compose down -v veri kaybettirir ve 00 Kafka lab verisini de siler.

Mini alıştırma

  1. Connector config/status endpoint'lerini çağırın, Kafka topic listesinde CDC topic'ini görün.
  2. Postgres order status'ını UPDATED yapıp Debezium op alanındaki update olayını bulun.
  3. Connect'i geçici durdurup DB değişikliği yapın, tekrar başlatın; slot ve connector offset'in replay davranışını inceleyin.
  4. orders.sql.lab topic'ine JSON yazıp ksqlDB stream filter query sonucunu gözleyin.
  5. CDC row event'i ile OrderPaid domain event'i arasındaki farkı açıklayın.

Kontrol noktası: CDC capture DB transaction log'undan row mutation taşır; domain event iş niyeti/semantiğidir. Birini diğerine otomatik eşitlemeyin.

Kısa özet

  • Connect source dışarıdan Kafka'ya, sink Kafka'dan dışarıya taşır.
  • Debezium log-based CDC ve snapshot/offset/schema history yönetir.
  • Kafka Streams Java topology ile, ksqlDB SQL query ile event akışını işler.
  • Her modülde offset, schema, lifecycle, lag, error/DLQ ve resource planı gerekir.

Kendini değerlendir

1. Source ve sink connector farkı nedir?

Source Kafka'ya data üretir; sink Kafka topic'lerini external system'e aktarır.

2. Debezium CDC event'i domain event midir?

Hayır; çoğunlukla row change envelope'ıdır. Domain intent için mapping/outbox gerekir.

3. PostgreSQL replication slot neden risklidir?

Consumer durunca gerekli WAL birikerek disk alanını tüketebilir.

4. Kafka Streams application.id neyi etkiler?

Consumer group kimliği ve internal state/changelog topic namespace'ini etkiler.

5. ksqlDB persistent query ne oluşturur?

Kafka topic'leri üzerinde çalışan, event okuyup yeni stream/table sonuçları üreten sürekli query/topology.
