Event-Driven Mimari Tasarımı

Event-driven architecture yalnızca REST çağrılarını Kafka'ya taşımak değildir. Bu modülde event'in iş sözleşmesini, servisler arası koordinasyonu ve veri sahipliğini birlikte tasarlayacağız.

Hedefler

1. Choreography ve orchestration

Choreography — neden?

Central coordinator darboğazını önlemek ve servislerin özerk kalması için kullanılır. Her servis kendi domain event'ini üretir, diğerleri abone olur.

Nasıl çalışır?

OrderCreated → Payment service PaymentAuthorized → Inventory service StockReserved → Notification service. Kafka broker akışı saklar; servisler ortak choreography kurallarını ve korelasyon kimliğini paylaşır.

Orchestration — neden?

Uzun ve görünür iş akışını tek bir process manager ile yönetmek, timeout/telafi adımlarını açıklaştırmak için.

Nasıl çalışır?

Saga orchestrator AuthorizePayment komutunu gönderir, yanıt/event bekler, sonra ReserveStock başlatır. Durum ve timeout'ları orchestrator saklar; orchestrator'ın yüksek erişilebilirliği ve state recovery tasarlanır.

Karar ölçütüChoreography uygunOrchestration uygun
Adım sayısı/branchAz, basit reaksiyonlar; servisler bağımsız.Çok adımlı, koşullu, timeout/telafili süreç.
OperasyonDağıtık akış gözlemi ve event causality gerekir.Merkezi process state ve orchestration endpoint'i izlenir.

İki desen birlikte kullanılabilir: bir saga orchestration'ın sonucunu domain event'i olarak yayınlar; diğer bağımsız consumer'lar choreography ile tepki verir.

2. Event notification ve event-carried state transfer

Event notification: “Sipariş değişti” bilgisini küçük payload ve aggregate ID ile bildirir; consumer detay için producer API'sini çağırabilir. Payload küçük ve gizlilik yüzeyi dardır, fakat runtime bağımlılık ve ekstra read çağrısı yaratır.

Event-carried state transfer: Consumer'ın ihtiyacı olan immutable state snapshot/delta event içine konur. Consumer bağımsız okuyup yerel projection tutabilir; event boyutu, veri çoğalması, schema evolution ve PII yönetimi yükü artar.

TercihÖrnek payloadDikkat
Notification{"orderId":"O-9","eventType":"OrderChanged","version":8}Consumer'a API erişimi, timeout ve API contract'ı gerekir.
Carried state{"orderId":"O-9","version":8,"currency":"TRY","total":420}Only consumer need-to-know alanları gönder; schema ve PII retention politikasını tanımla.

Event'leri geçmiş zamanla adlandırın (OrderCreated, PaymentDeclined); command'ı event gibi adlandırmayın. Event immutable geçmiş gerçeğidir; düzeltme yeni event ile modellenir.

3. Event sourcing

Neden? Mevcut state'in nasıl oluştuğunu denetlemek, geçmişi replay etmek ve domain değişikliklerini izlemek gerekebilir.

Nasıl? Aggregate state'i güncel satırdan değil, sıralı domain event'lerinin fold/reduce edilmesinden elde edilir. Command validate edilir, event append edilir; snapshot replay süresini azaltabilir. Kafka topic'i event-sourced store olarak otomatik/sonsuz saklama, optimistic concurrency, aggregate transaction veya per-entity stream semantics vermez. Compaction/retention ve replay policy açık olmalıdır.

  • Event store için append-only, aggregate version, idempotent append ve optimistic concurrency tasarlayın.
  • Kafka topic'i integration event distribution için tutup domain event store'u ayrı tutmak çoğu sistemde daha net sınır verir.
  • Replay side effect çalıştırmamalı; projection rebuild yolu canlı bildirim/e-posta tetiklememeli.
  • PII silme/yasal retention gereksinimleri append-only geçmişle çatışabilir; tasarımda baştan çözün.

CLI gözlemi, integration event log'unu ve replay'i gösterir; tek başına event sourcing'in aggregate concurrency garantisini göstermez:

docker exec kafka-lab /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders.events --from-beginning --property print.key=true --property print.partition=true --property print.offset=true

4. CQRS: command ve query sorumluluklarını ayırma

Neden? Yazma domain modelinin invariant'ları ile okuma ekranlarının sorgu/latency ihtiyaçları aynı şekle uymayabilir.

Nasıl? Command model iş kurallarını uygular; başarıyla kabul edilen değişiklik event olarak yayımlanır. Consumer projection, query modelini async günceller. Okuma hızlı/özelleştirilmiş hale gelir; karşılığında eventual consistency, projection rebuild, lag ve schema migration yönetilir.

CQRS = event sourcing değildir. CQRS aynı veritabanında ayrı modelle de yapılabilir; event sourcing CQRS ile birleştirilebilir ama zorunlu değildir. Kafka genelde projection güncelleme taşıyıcısı olabilir, query DB'nin yerine geçmez.

docker exec kafka-lab /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group order-read-model

Beklenen: consumer çalışırken assignment, committed/current offset ve lag sütunları. Read model lag'i UI'da “son güncelleme zamanı” gibi açıklanabilir; kullanıcıya henüz görünmeyen değişikliği stale response olarak yönetin.

Yeni ek bileşen gerekmiyor: 00 numaralı Apache Kafka KRaft broker'ını ve 01'deki orders.events topic'ini kullanın. Docker Compose dosyası 00'da hazırlanmıştır; aşağıdaki işletim sistemi sekmeleri aynı komutları gösterir. Terminali Compose proje klasöründe açın.

Producer/consumer komutları interaktiftir; ayrı terminal kullanın ve Ctrl+C ile çıkın. Key/value olarak O-100:OrderCreated ve O-100:PaymentAuthorized girin. Tüketici çıktısında event key'i aynı aggregate ID; partition aynı kaldıysa aynı partition sırasını gözlemleyin.

Container içindeki demo CLI dışında Java servislerini host'ta çalıştırıyorsanız bootstrap server localhost:9092; aynı Compose network içinden bağlanıyorsanız broker:19092.

6. Event contract, sık yapılan hatalar ve operasyon checklist

  • Event'in owner servisi, adı, semantiği ve consumer listesi belli mi?
  • Event key'i aggregate/partition ordering ihtiyacına uygun mu?
  • Event ID, aggregate ID/version, occurredAt, correlation/causation ID var mı?
  • Consumer duplicate, out-of-order, replay ve unknown event version ile güvenli mi?
  • Retry/DLT, lag, event age ve iş metriği alarmı mevcut mu?
  • PII minimizasyonu, retention, ACL, encryption, data residency gözden geçirildi mi?
  • Schema compatibility policy ve topic lifecycle owner'ı belirli mi?

Sık yapılan hatalar: event'i command gibi kullanmak; producer API'sini her consumer'a senkron çağrıya dönüştürmek; topic-wide ordering varsaymak; event sourcing ile Kafka'yı eşitlemek; consumer duplicate/lag/replay davranışını planlamamak; event'e gereksiz PII eklemek.

Event-driven tasarım synchronous request-response ihtiyacını ortadan kaldırmaz. Kullanıcıya anında kesin sonuç sunmak gerekiyorsa komut kabulü ile nihai iş sonucu arasındaki durum açıkça modellenmelidir.

Mini alıştırma

Sipariş onay akışı için iki tasarım çizin:

  1. Choreography: Order → Payment → Inventory → Notification event'leri, her servisin group ID'si ve olası hata/telafi event'i.
  2. Orchestration: saga state, komutlar/yanıtlar, timeout ve ödeme başarılı fakat stok yok durumundaki compensation.
  3. Liste ekranı için event notification veya carried state seçin; veri gizliliği, API bağımlılığı ve eventual consistency gerekçenizi yazın.
  4. Bu akışta CQRS kullanıp kullanmadığınızı ve event sourcing'in gerçekten gerekli olup olmadığını açıklayın.

Kontrol noktası: Notification ve carried state arasında tek doğru yoktur; consumer bağımsızlığı, veri hassasiyeti ve payload yönetimi açık gerekçelendirilmelidir.

Kısa özet

  • Choreography dağıtık tepkiyi, orchestration süreç kontrolünü öne çıkarır.
  • Notification küçük sinyal; carried state daha bağımsız consumer karşılığında daha büyük contract'tır.
  • Event sourcing ve CQRS farklı kavramlardır; Kafka bunların yerine otomatik çözüm değildir.
  • Eventual consistency, idempotency, replay, privacy ve observability tasarımın parçasıdır.

Kendini değerlendir

1. Choreography'nin temel riski nedir?

Event zinciri ve bağımlılıkların merkezi görünürlüğünün azalması; causality, döngü ve hataları izlemek zorlaşır.

2. Event notification'ın temel trade-off'u nedir?

Küçük payload sağlar; consumer detay almak için producer API'sine bağlanabilir.

3. Event sourcing için Kafka topic tek başına yeterli midir?

Hayır. Aggregate concurrency, append semantics, replay safety, retention ve PII policy ayrıca ele alınmalıdır.

4. CQRS event sourcing'i zorunlu kılar mı?

Hayır. CQRS ayrı command/query modelidir; aynı DB üzerinde de uygulanabilir.

5. Kafka event consumer'da duplicate görülebilir mi?

Evet. At-least-once retry/crash durumlarında duplicate olabileceği için idempotency gerekir.
