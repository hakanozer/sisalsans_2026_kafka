1. Idempotent consumer

Neden? Consumer dış DB'ye yazdıktan sonra offset commit etmeden çökerse Kafka aynı record'u yeniden sunar. Network timeout'ta producer send başarısız görünüp broker'a yazılmış da olabilir. “Bir kere gelir” varsayımı iş verisini bozabilir.

Nasıl? Her event'e producer tarafında kalıcı unique eventId verin. Consumer DB transaction'ında önce processed-event tablosuna eventId insert eder; unique constraint çakışırsa event daha önce uygulanmıştır. Insert ve business update aynı DB transaction'ında commit olmalıdır.

CREATE TABLE processed_event (
  consumer_name VARCHAR(120) NOT NULL,
  event_id UUID NOT NULL,
  processed_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (consumer_name, event_id)
);

CREATE TABLE order_projection (
  order_id VARCHAR(200) PRIMARY KEY,
  status VARCHAR(80) NOT NULL
);

JDBC'de PostgreSQL örneği, duplicate'i kontrollü yakalamak için INSERT ... ON CONFLICT DO NOTHING kullanabilir. Sadece unique violation'ı yutup başka DB hatalarını yutmayın. DB commit'ten sonra Kafka offset commit başarısız olursa duplicate yeniden gelir; unique kayıt yan etkiyi bir kez uygular, offset yeniden commit edilebilir.

@Service
public class IdempotentOrderProjection {
    private final JdbcTemplate jdbc;

    public IdempotentOrderProjection(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    @Transactional
    public void apply(String eventId, OrderEvent event) {
        int inserted = jdbc.update("""
                INSERT INTO processed_event(consumer_name, event_id)
                VALUES ('order-projection', ?::uuid)
                ON CONFLICT DO NOTHING
                """, eventId);
        if (inserted == 0) {
            return; // Bu consumer bu event ID'yi daha önce uygulamış.
        }
        jdbc.update("""
                INSERT INTO order_projection(order_id, status) VALUES (?, ?)
                ON CONFLICT (order_id) DO UPDATE SET status = EXCLUDED.status
                """, event.orderId(), event.status());
    }
}

Listener bu metodu çağırır ve yalnız başarıyla döndükten sonra offset'i commit eder; DB işlemi rollback olursa processed-event insert'i de rollback olur. JSON event'e producer tarafında stable event ID ekleyin. PostgreSQL UUID kolonu için Java tarafında UUID tipi kullanmak tercih edilir; örnekte ?::uuid ile string parametre cast edilmiştir.

Sınır: Idempotency key kapsamı consumer adı + event ID olmalıdır; iki bağımsız projection aynı event'i işleyebilir. Processed-event kaydının retention'ı, replay ve yasal saklama planıyla uyumlu olmalı. Idempotency tek başına event sıralamasını, dış API'nin exactly-once davranışını veya yanlış business key'i çözmez.

2. Transactional outbox

Neden? Bir request hem order DB'sini güncelleyip hem Kafka'ya event yayınlarsa iki bağımsız write oluşur: DB commit olup publish başarısız olabilir veya Kafka publish olup DB rollback olabilir. Bu dual-write atomik değildir.

Nasıl? Tek DB transaction'ında business row ve outbox row yazılır. Ayrı relay/poller ya da CDC connector outbox row'u Kafka'ya aktarır. Publish sonrası outbox kaydı delivered/retained işaretlenir; crash durumunda tekrar gönderilebilir, dolayısıyla event ID ile consumer idempotency yine gerekir.

CREATE TABLE outbox_event (
  event_id UUID PRIMARY KEY,
  aggregate_type VARCHAR(120) NOT NULL,
  aggregate_id VARCHAR(200) NOT NULL,
  event_type VARCHAR(200) NOT NULL,
  payload JSONB NOT NULL,
  occurred_at TIMESTAMP NOT NULL,
  published_at TIMESTAMP NULL
);

-- Uygulama DB transaction'ı:
-- UPDATE orders SET status = 'CREATED' WHERE id = :id;
-- INSERT INTO outbox_event(event_id, aggregate_type, aggregate_id,
--   event_type, payload, occurred_at)
-- VALUES (:eventId, 'Order', :orderId, 'OrderCreated', :json, now());

Polling relay'e ilişkin basitleştirilmiş SQL seçimi:

SELECT event_id, aggregate_id, event_type, payload
FROM outbox_event
WHERE published_at IS NULL
ORDER BY occurred_at
FOR UPDATE SKIP LOCKED
LIMIT 100;

Örnek PostgreSQL'dir; DB dialect'ine göre SQL farklılaşır. Worker kayıtları transaction'da kilitler, Kafka'ya gönderir, yalnız ack geldikten sonra published işaretler. Broker ack ile DB published commit arasında crash tekrar publish doğurabilir: event ID zorunludur. Uzun süre DB lock tutmayın; leasing/claim state ve poll batch ölçümü planlayın.

Spring ile DB transaction sınırı

@Service
public class OrderCommandService {
    private final JdbcTemplate jdbc;

    public OrderCommandService(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    @Transactional
    public void createOrder(long id, String eventId, String jsonPayload) {
        jdbc.update("INSERT INTO orders(id, status) VALUES (?, 'CREATED')", id);
        jdbc.update("""
                INSERT INTO outbox_event(event_id, aggregate_type, aggregate_id,
                    event_type, payload, occurred_at)
                VALUES (?::uuid, 'Order', ?, 'OrderCreated', ?::jsonb, now())
                """, eventId, Long.toString(id), jsonPayload);
    }
}

Bu Spring @Transactional method'u iki JDBC write'ı aynı datasource transaction'ında yürütür. Kafka publish bu transaction'a eklenmez; outbox relay/CDC ayrı süreçtir. DB driver, table schema ve transaction manager'ın aynı datasource'u kullandığını doğrulayın.

CDC ile outbox

Debezium Outbox Event Router gibi CDC yaklaşımı DB transaction log'undan outbox row değişikliklerini okur; polling yükünü azaltabilir ama connector lifecycle, schema, snapshot, DB replication privileges, log retention ve connector offset'leri işletilmelidir. CDC'nin kurulum adımı Modül 05'te uygulanır.

3. Kafka transaction ve exactly-once

Neden? Kafka topic'inden okuyup Kafka topic'ine sonuç yazan stream processor'da output record'ları ile input offsets birlikte commit edilmelidir. Aksi durumda output duplicate veya input kaybı doğabilir.

Nasıl? Transactional producer, output records ve consumed offsets'i Kafka transaction'ında yazar/commit eder. Consumer isolation.level=read_committed kullanıp yalnız commit edilmiş transactional event'leri görür. Transaction ID her uygulama instance'ında unique olmalı; partition/task sahipliği değişince eski producer'ı fence etme mekanizması vardır.

spring:
  kafka:
    producer:
      transaction-id-prefix: order-tx-${INSTANCE_ID}-
      acks: all
      properties:
        enable.idempotence: true
    consumer:
      enable-auto-commit: false
      properties:
        isolation.level: read_committed
    listener:
      ack-mode: record

INSTANCE_ID her concurrently çalışan app instance için unique ve restart'ta çakışmayacak şekilde olmalıdır. Spring Boot transaction prefix ile transactional producer/template oluşturabilir. Aşağıdaki bean'i yalnızca Boot uygulamanız aynı manager'ı auto-configure etmiyorsa tanımlayın; iki kez bean üretmeyin. Spring Kafka Kafka transaction manager'ı Kafka resource transaction'ını yönetir; JPA/DB ile global XA transaction anlamına gelmez.

@Configuration
public class KafkaTransactionConfiguration {
    @Bean
    KafkaTransactionManager<String, Object> kafkaTransactionManager(
            ProducerFactory<String, Object> producerFactory) {
        return new KafkaTransactionManager<>(producerFactory);
    }
}

Spring bean imports: org.springframework.kafka.transaction.KafkaTransactionManager ve org.springframework.kafka.core.ProducerFactory. Boot auto-configuration kullanıyorsanız named manager bean'ini enjekte edin.

@Service
public class EnrichmentService {
    private final KafkaTemplate<String, EnrichedOrder> template;

    public EnrichmentService(KafkaTemplate<String, EnrichedOrder> template) {
        this.template = template;
    }

    @Transactional("kafkaTransactionManager")
    public void emit(String orderId, EnrichedOrder result) {
        template.send("orders.enriched", orderId, result);
    }
}

Uygulama kodundaki method transactional Kafka manager ve producer transaction prefix ile çalışır. Gerçek consume-transform-produce için listener container transaction'ı input offsets ile bağlamalı; yalnız @Transactional method yeterli değildir. Boot sürümüne uygun listener container wiring'i integration test ile doğrulayın.

Exactly-once kapsamı: Kafka consume → transform → Kafka produce/offset akışında Kafka içinde atomiklik sağlayabilir. Bankaya HTTP çağrısı, e-posta gönderimi veya DB side effect aynı Kafka transaction'ına dahil değildir. Dış yan etkiler için outbox, inbox/idempotency, provider idempotency key ve saga düşünün.

Önemli konfigürasyonlar: producer transactional.id (Spring prefix), enable.idempotence, acks=all; consumer isolation.level=read_committed; topic replication ve min.insync.replicas production dayanıklılığına göre. Tek broker lab replication=1 olduğu için HA/EOS production kanıtı değildir.

4. Retry stratejisi ve Dead-Letter Topic

Neden? Geçici DB/network hataları tekrar denemeyle düzelebilir. Geçersiz payload gibi kalıcı hata sonsuz retry ile partition'ı bloke edebilir.

Nasıl? Hataları transient/permanent sınıflandırın; sınırlı attempt ve backoff uygulayın; sonrasında DLT'ye key, payload, original topic/partition/offset, exception sınıfı ve timestamp header'larıyla gönderin. DLT event'i triage, redrive ve audit süreciyle ele alınır.

@Configuration
class ErrorConfig {
    @Bean
    DefaultErrorHandler errorHandler(KafkaTemplate<Object, Object> template) {
        var recoverer = new DeadLetterPublishingRecoverer(template);
        var handler = new DefaultErrorHandler(
                recoverer, new ExponentialBackOffWithMaxRetries(4));
        handler.addNotRetryableExceptions(IllegalArgumentException.class);
        return handler;
    }
}

Import: org.springframework.kafka.listener.ExponentialBackOffWithMaxRetries. Constructor/method ayrıntısını Spring Kafka 4.1.1 API'sinde doğrulayın. DeadLetterPublishingRecoverer varsayılan hedefi original topic + .DLT, partition routing davranışını production'da açıkça seçip DLT partition sayısını uygun tutun. Retry sırasında aynı partition'daki sonraki event'lerin bloklanma etkisini değerlendirin; retry topic yaklaşımı sıralamayı değiştirir ve ayrı topic/consumer operasyonu ister.

Retry karar tablosu

HataPolitika
DB timeout / kısa süreli dependency unavailableKısa bounded retry; gecikme/backoff; maksimum süre ve load shedding.
Schema/validation permanent rejectHızlı DLT veya quarantine; retry yok ya da çok az.
Authorization/configurationBlind retry yapmayın; alarm ve düzeltme.
DLT publish failureRecoverer hata görünür olsun; log/metric/alarm, container failure policy ve replay prosedürü tanımlı.

DLT consumer'ı DLT'yi otomatikçe ana topic'e sürekli geri basmamalı; poison loop oluşur. Redrive öncesi payload düzeltme, schema compatibility, event idempotency ve audit bilgisi kaydedin.

Beklenen: yalnız retry limitinden sonra recover edilen event DLT'de görünür; headers içinde original topic/partition/offset ve exception metadata bulunur. Exact header listesi Spring Kafka version ve serializer'a göre değişebilir. Consumer group offset'lerini izleyin:

docker exec kafka-lab /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group order-processor

Hatalar, önemli ayarlar ve iyi uygulamalar

  • Outbox row'u business update'ten ayrı transaction'a yazmak dual-write sorununu geri getirir.
  • Kafka ack alınmadan outbox row'u published işaretlemek event kaybettirebilir; ack sonrası DB commit crash'i duplicate üretebilir, idempotency şarttır.
  • Kafka EOS'yi harici DB/email/payment için genel exactly-once sanmak.
  • Sınırsız retry, retry storm ve consumer lag yaratır. Backoff exponential + max attempt + retry budget belirleyin.
  • acks=all, enable.idempotence=true, retries, max.in.flight.requests.per.connection uyumlu yapılandırılmalı; acks=all tek başına durable quorum değildir.
  • min.insync.replicas, replication factor ve broker sayısı birlikte seçilir. RF=1 tek node arızasına dayanmaz.
  • DLT'ye yazma hatası da failure'dır: metric/alarm ve güvenli recovery sağlayın.
  • Consumer ack/commit business işleminin commit sırasına göre yapılmalı; DB transaction ve Kafka offset için gerçek transaction sınırını test edin.

Mini alıştırma

  1. Consumer DB update yaptıktan hemen sonra, offset commit'ten önce öldürün. Redelivery ve processed_event unique constraint davranışını gözlemleyin.
  2. Outbox publish ack sonrası fakat published_at commit öncesi crash senaryosunu çizin. Hangi duplicate koruması gerekir?
  3. Bir transient timeout ve bir permanent validation hatası tanımlayıp retry/DLT politikasını yazın.
  4. Kafka transaction ile outbox'ın hangi farklı problemi çözdüğünü açıklayın.

Kontrol noktası: Uçtan uca at-least-once + idempotent side-effect çoğu kurumsal iş yükünde yönetilebilir güvenilirlik hedefidir. “Exactly-once” ifadesinin transaction scope'u belirtilmelidir.

Kısa özet

  • Consumer duplicate'leri business event ID ve DB unique constraint ile yönetilebilir.
  • Transactional outbox DB business state ile yayın niyetini aynı transaction'a alır; relay/CDC duplicate üretebilir.
  • Kafka transaction Kafka output ve offset commitini atomik yapar; harici sistemleri kapsamaz.
  • Bounded retry/backoff, DLT, idempotency ve alarm birlikte tasarlanır.

Kendini değerlendir

1. DB update sonrası offset commit öncesi crash ne doğurur?

Record yeniden tüketilebilir; DB side effect idempotent değilse duplicate uygulanır.

2. Outbox pattern dual-write'ı nasıl azaltır?

Business update ve outbox row aynı DB transaction'ında commit edilir; relay daha sonra yayınlar.

3. Kafka transaction harici DB commit'ini kapsar mı?

Hayır; Kafka resource/offset sınırında atomiklik sağlar.

4. DLT neden otomatik sonsuz redrive edilmemeli?

Poison message retry loop ve sürekli failure yaratabilir; triage ve kontrollü redrive gerekir.

5. Idempotent producer consumer business duplicate'lerini çözer mi?

Hayır; producer protocol retry duplicate riskini azaltır, application-level duplicate'e consumer idempotency gerekir.
